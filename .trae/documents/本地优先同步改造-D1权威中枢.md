# 本地优先同步改造 —— Cloudflare Worker + D1 权威中枢 + 登录 + MCP

## Context（为什么做这件事）

「柠檬百宝箱」是给一个人做的本地优先 App：本地 Room 主库离线可用，多设备要能对上。
现在多台设备**每天都会手动同步**，却长期出现四类不一致，且**完全没有提示、无法定位**：

- 家当/待办的**条数与其它设备不同**
- 改名等**内容改了却被还原**
- **照片缺失**但条目在

### 事实更正（本轮）

此前计划把对象存储写成 Cloudflare R2，并据此推导出「Worker 调 R2 `temp-access-credentials`」的路线，**这是错的**，作废。核查结论：

- 代码里**没有任何厂家硬编码**。客户端走通用 path-style（`endpoint/bucket/key`），[S3Signer.kt](file:///e:/Downloads/lemonbox/app/src/main/java/com/goodyaoshi/lemonbox/data/imagecloud/S3Signer.kt) 是标准 AWS SigV4（service 固定 `s3`）；注释与 README 里的 R2 只是**举例**（[S3ImageClient.kt](file:///e:/Downloads/lemonbox/app/src/main/java/com/goodyaoshi/lemonbox/data/imagecloud/S3ImageClient.kt#L120-L122)）。
- endpoint / region / bucket / prefix / AK / SK 全部来自构建期注入的**密文**，仓库内看不到真实值（仅 `DEFAULT_REGION = "auto"` 是个带 R2 注释的兜底常量）。
- 用户确认：对象存储是**自建 S3 兼容存储**（非 R2）。

## 目标架构

```
Android App（本地优先，Room 主库）
  │  未登录 → 纯本地，同步入口提示登录
  │  已登录（Bearer session token）
  ▼
Cloudflare Worker（唯一后端，持有全部长期密钥）
  ├── D1            ← 记录权威存储（server_seq 单调序号）
  ├── Blob 预签名    ← 自建 S3 兼容存储的 AK/SK 只存在 Worker；客户端每次只拿几分钟有效的 URL
  └── /mcp          ← 同一 Worker 兼作 MCP 服务端（读写、禁删）→ AI 整理家庭数据
```

关键点：
- **记录数据放 D1**，以服务端单调 `server_seq` 取代墙钟 LWW 与 SharedPreferences 水位线。
- **对象存储密钥不下发**：Worker 持自建 S3 的 AK/SK，客户端只拿**预签名 URL**（上传/下载）与**服务端代执行**的探在/删除/列举/自检。
- **登录即启用云同步**：账号由服务端预置（一人一个），密码不下发到客户端。
- **不做 Room 触发器**（评估后否决）：本地编辑与同步落地的 `UPDATE` 语句形态完全相同，只能靠弱信号区分；且触发器不进 Room `exportSchema` 校验。改为**直接修 6 处漏刷 + 白名单单测兜底**。

## 决策记录

| 项 | 决定 |
|---|---|
| 记录权威 | Cloudflare D1 + Worker，服务端单调 `server_seq` |
| 对象存储 | 用户自建 S3 兼容存储，**保持不动**；密钥移到 Worker |
| 临时授权形态 | **Worker 下发预签名 URL**（不做 STS 临时凭证、不做 R2 原生临时凭证） |
| 客户端签名 | 客户端**不再参与 SigV4**；SigV4 只在 Worker 里实现 |
| 登录 | 服务端预置账号密码（一人一个），登录后可显示「这条最后是谁改的」 |
| 未登录 | 纯本地，不出现任何云入口的可用态 |
| 旧口令机制 | `S3_PAYLOAD_ENCRYPTED` + 口令解锁**彻底移除** |
| MCP | 同一 Worker 提供 `/mcp`；静态 Bearer token 先行，OAuth Portal 预留 |
| MCP 权限 | **读写、禁止删除** |
| 冲突 | push 带 `baseSeq` 乐观并发，服务端返回 conflict 而不覆盖 |
| 载荷格式 | 复用 `BackupSnapshots.kt` 的 Snapshot DTO，**绝不直接序列化实体** |

## 服务端设计

### D1 Schema

```sql
CREATE TABLE meta (k TEXT PRIMARY KEY, v INTEGER NOT NULL);
INSERT INTO meta(k,v) VALUES('seq', 0);

-- 记录：一条 (collection, record_key) 一行，payload 是该实体的 Snapshot JSON
CREATE TABLE records (
  collection      TEXT NOT NULL,      -- items / reminders / ledger_records / ...
  record_key      TEXT NOT NULL,      -- Snapshot.syncId（跨设备引用靠它，禁用本机自增 id）
  payload         TEXT NOT NULL,      -- Snapshot JSON（含 tombstone 的 deletedAt/purgedAt）
  server_seq      INTEGER NOT NULL,
  updated_by_user TEXT NOT NULL,      -- 人（用于「最后是谁改的」）
  updated_by_dev  TEXT NOT NULL,      -- 设备（pull 时排除自己，同人多设备互不误排）
  updated_at      INTEGER NOT NULL,
  deleted         INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (collection, record_key)
);
CREATE INDEX idx_records_seq ON records(server_seq);
CREATE INDEX idx_records_coll_seq ON records(collection, server_seq);

CREATE TABLE users (
  id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE,
  salt TEXT NOT NULL, iterations INTEGER NOT NULL, hash TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE TABLE sessions (
  token_hash TEXT PRIMARY KEY, user_id TEXT NOT NULL,
  device_id TEXT NOT NULL, expires_at INTEGER NOT NULL, created_at INTEGER NOT NULL
);
CREATE TABLE devices (
  device_id TEXT PRIMARY KEY, user_id TEXT, name TEXT,
  last_seen_at INTEGER, last_pull_seq INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE conflicts (
  id INTEGER PRIMARY KEY AUTOINCREMENT, collection TEXT, record_key TEXT,
  base_seq INTEGER, server_seq INTEGER, by_device TEXT, at INTEGER
);
```

### 接口契约（除 `/v1/login`、`/v1/admin/*` 外均需 `Authorization: Bearer <session token>`）

- `POST /v1/login` `{username, password, deviceId, deviceName}` → `{token, expiresAt, user:{id,name}}`
  - 密码校验：PBKDF2-HMAC-SHA256（WebCrypto），比对 `users.hash`；token 为 32 字节随机值，库里只存 `sha256(token)`，TTL 90 天。
- `POST /v1/logout` → 删会话。
- `POST /v1/admin/users`（`X-Admin-Token`，**不进 App**）→ 建号 / 改密；账号只在服务端配置。
- `POST /v1/push` `{deviceId, baseSeq, changes:[{collection, key, payload, deleted}]}`
  - 一次领号：`UPDATE meta SET v = v + N WHERE k='seq' RETURNING v`；
  - 按 D1「单条 SQL ≤100 绑定参数」约束分批（`records` 7 列 → 每语句 ≤12 行），用 `db.batch()`；
  - 对 `server_seq > baseSeq` 的条目**写 conflicts 而不覆盖**；
  - **客户端单次只推 ≤200 条**，响应带 `done:false/hasMore` 让客户端继续（避开 Workers 免费档 CPU 上限）。
- `GET /v1/pull?since=&limit=500&deviceId=` → `{changes, lastSeq, hasMore}`
  - `WHERE server_seq > ? AND updated_by_dev <> ? ORDER BY server_seq LIMIT ?`；
  - `hasMore` 为真时客户端**不推水位**，下一轮接着拉。
- `GET /v1/stats` → 各 collection 的 live/deleted 计数、设备列表（名字/`last_seen_at`/`last_pull_seq`）、未决冲突数。

### Blob API（自建 S3 兼容存储；客户端不持密钥）

Worker 内实现 SigV4（HMAC-SHA256 走 WebCrypto），用 Worker secrets 里的 AK/SK 签：

- `POST /v1/blob/url` `{key, op:"get"|"put", ttlSeconds≤600}` → `{url, expiresAt}`
  - 预签名用 `UNSIGNED-PAYLOAD`，只签 `host`（与现有 [S3Signer.presignedUrl](file:///e:/Downloads/lemonbox/app/src/main/java/com/goodyaoshi/lemonbox/data/imagecloud/S3Signer.kt#L52-L94) 同一套语义）；
  - `op:"put"` 供客户端直传字节，`op:"get"` 供 Coil 与本机下载。
- `POST /v1/blob/probe` `{key}` → `{exists, size}`：Worker 服务端 HEAD。**不给客户端 HEAD 用 URL**——预签名与方法是绑定的，改方法必然 403（见 [S3ImageClient.kt](file:///e:/Downloads/lemonbox/app/src/main/java/com/goodyaoshi/lemonbox/data/imagecloud/S3ImageClient.kt#L330-L338) 的既有教训）。
- `POST /v1/blob/delete` `{key}` → Worker 服务端删。删除权限**永远不下发**，客户端拿不到可删除的授权。
- `GET /v1/blob/list?prefix=` → Worker 服务端 ListObjectsV2 并返回 JSON（不再返回 XML 让客户端解析）。
- `GET /v1/blob/selfcheck` → Worker HEAD 桶根，返回通/不通与原因（把「endpoint/region/凭据是否走得通」整体挪到服务端）。

### MCP（同一 Worker，`/mcp`）

- 传输：MCP Streamable HTTP，JSON-RPC `initialize` / `tools/list` / `tools/call`，响应 JSON。
- 鉴权：`Authorization: Bearer <MCP_TOKEN>`（Worker secret）；后续接官方连接器时再加 OAuth，鉴权抽一层。
- 工具（**读写、无删除**）：`list_items` / `search_items` / `get_item` / `add_item` / `update_item`、`list_reminders` / `add_reminder` / `update_reminder`、`list_ledger_records` / `add_ledger_record` / `update_ledger_record`、`list_categories`、`list_locations`、`shopping_list`。
- 写入语义：读 `records` 行 → 改 Snapshot JSON → 领新 `server_seq` 写回（`updated_by_user = "AI助手"`，`updated_by_dev = "mcp"`），App 下次 pull 即收到并可显示「由 AI 助手修改」。
- 工具入参用 Snapshot 的字段名（`syncId` 而非本机 id），避免把本机自增 id 带进 D1。

### 部署方式

仓库当前**无任何后端产物**（无 `server/`、无 npm/wrangler）。新建 `server/`：

- `server/worker.js` —— 单文件 ES module（**无 npm 依赖、无打包步骤**），`export default { fetch }`。
- `server/schema.sql` —— 上面的 D1 schema。
- 用已连接的 Cloudflare MCP 直接建资源（endpoint 已核实存在）：
  1. `POST /accounts/{account_id}/d1/database` 建库 → `POST .../query` 执行 schema；
  2. `PUT /accounts/{account_id}/workers/scripts/{name}` 以 multipart（`metadata.main_module = "worker.js"` + `Content-Type: application/javascript+module`）上传；
  3. `PUT /accounts/{account_id}/workers/scripts/{name}/secrets` 逐个写入 `S3_*`、`ADMIN_TOKEN`、`MCP_TOKEN`；
  4. `PUT /accounts/{account_id}/workers/subdomain` 拿到 `*.workers.dev` 域名。
- 权限不足时走 `RequestAuthorization`。

## 阶段划分

- **P1 服务端骨架**：D1 建库+建表、Worker（登录/会话/设备/健康检查）、`/v1/admin/users` 建两个账号、部署、secrets 写入。
- **P2 同步 API**：`/v1/push`（领号+分批+`baseSeq` 冲突）、`/v1/pull`（分页+排除自己）、`/v1/stats`；`curl` 往返自测。
- **P3 Blob API**：SigV4 预签名（`/v1/blob/url`）+ probe/delete/list/selfcheck；**先用 `curl` 拿 Worker 给的预签名 URL 对真实自建桶跑通 PUT/GET**，再谈接客户端。
- **P4 客户端登录与鉴权**：会话存储、`RemoteSyncClient`、登录页、移除旧口令链路（含 CI/README/build.gradle）。未登录 = 纯本地。
- **P5 全量推拉**：`snapshotRecords()` + `RemoteSyncManager.syncNow()`（首次全量 push / `since=0` 分页 pull → 重组 → `importBackup` 落地 → 回执）。
- **P6 增量化与可靠性**：`MIGRATION_36_37`（dirty/serverSeq）+ `sync_state` 表（水位入库同事务）+ 分批 + `hasMore` + 冲突上报 + 墓碑清除加「服务端已确认」前提。
- **P7 修 6 处漏刷 + 防回归单测**：白名单扫描所有 `@Query("UPDATE ...")`。
- **P8 图片链路切换**：`BlobGateway` 接 `ImageCloudSyncManager` / `ImageUrlResolver`。
- **P9 对账/诊断页**：逐表三方计数（本机 live / 本机含墓碑 / 服务端 live / 差集）、`syncId` 为空的旧行数量、冲突逐条（复用 [ConflictFieldDiffLine](file:///e:/Downloads/lemonbox/app/src/main/java/com/goodyaoshi/lemonbox/ui/components/FieldDiffViews.kt#L72-L111)）、设备列表、「立即对账」、「以服务端为准重建本地」（危险操作：二次确认 + 撤销回执）。
- **P10 MCP 服务端**：`/mcp` JSON-RPC + 读写工具（禁删）+ 静态 Bearer；用 MCP 客户端实际调一次「整理待买清单」验证闭环。
- **P11 局域网 ZIP 同步对齐（可选）**：`mergeXxx` 的落地写增加「标脏」参数（本地合并标脏、同步导入不标脏），让服务端保持唯一权威。

- 全程不与 GitHub 大流量交互（项目硬规则；本方案不涉及 GitHub 传输）。

## 风险与对策

1. **Worker SigV4 预签名的正确性**：签歪只表现为 403，极难定位。→ P3 先用 `curl` 对真实自建桶跑通 PUT/GET 再往下做；只签 `host`、`UNSIGNED-PAYLOAD`、path-style 寻址，UTC 时间。
2. **Workers 免费档 CPU 上限**：首次全量 push 数千行可能被 CPU 限流。→ 客户端单次 push ≤200 行、pull ≤500 行、按 `hasMore` 续跑；仍不够则升级 Workers 付费档（成本极低）。
3. **D1 单条 SQL ≤100 绑定参数**：`records` 7 列 → 每语句 ≤12 行，用 `db.batch()`。
4. **载荷误用实体直序列化**：会把本机 `id` 带过去造成外键指错行。→ 强制走 `BackupSnapshots` DTO，`record_key` 用 `syncId`。
5. **迁移 + 回填**：先在真机数据副本上验证；`app/schemas` 已导出 schema，迁移后审查 schema JSON 差异。
6. **旧设备仍在跑老版本**：会继续往对象存储写 ZIP 快照。→ 升级全部设备；D1 与 S3 命名空间互不干扰，老版本不破坏新链路。
7. **密钥一旦落到日志/包内即失效**：自建桶 AK/SK 只写进 Worker secrets，不进仓库、不进 APK、不进日志；`SYNC_BASE_URL` 是非密钥可进包。
8. **不做字段级合并**：这 14 张表字段强耦合（数量/价格/状态联动），收益低风险高；改为冲突逐条上报。
9. **两台设备的存量分歧**：收敛操作必须可见、可撤销，禁止无反馈的一键覆盖。
10. **MCP 面向 AI 的写权限**：只给读写、不给删；写入一律留 `updated_by="AI助手"` 可追溯。
